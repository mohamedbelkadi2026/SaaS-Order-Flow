Ce n'est plus un cas isolé, c'est un mismatch massif et actif qui continue de s'aggraver à chaque nouvelle commande.

## Cause : le bug `normStr()` (déjà identifié précédemment) n'est probablement toujours pas corrigé en production, ou pas correctement

Rappel du bug : dans **`server/services/variants.ts`**, `normStr()` supprime tout caractère non-latin (`.replace(/[^a-z0-9]+/g, ' ')`), donc TOUS les noms de produits arabes se normalisent vers la même chaîne (vide/espaces). `resolveProductId()` matche alors n'importe quel produit arabe au hasard (le premier trouvé) au lieu du bon.

**Avant de faire quoi que ce soit d'autre : vérifier en premier si ce fix a bien été appliqué et déployé.** Si oui, il y a un AUTRE bug qui produit le même symptôme (voir section "Si le fix normStr est déjà en place" plus bas) — ne pas réappliquer le même patch en boucle sans vérifier l'état actuel du fichier.

### Fix `normStr()` à confirmer/appliquer :
```ts
export function normStr(s: string): string {
  return (s || '')
    .normalize('NFKD')
    .replace(/[\u0300-\u036f]/g, '')
    .replace(/[\u064B-\u065F\u0670\u0640]/g, '')  // strip Arabic tashkeel/tatweel
    .replace(/[\u00A0\u2000-\u200B\t\n\r]/g, ' ')
    .toLowerCase()
    .replace(/[^a-z0-9\u0600-\u06FF\u0750-\u077F\u08A0-\u08FF\uFB50-\uFDFF\uFE70-\uFEFF]+/g, ' ')
    .trim()
    .replace(/\s+/g, ' ');
}
```

## Garde-fou supplémentaire — INDISPENSABLE pour empêcher que ça recommence

Peu importe le bug exact, le vrai problème de fond est que `resolveProductId()` **ne doit JAMAIS lier une commande à un produit "par défaut"/au hasard** quand il ne trouve pas de correspondance fiable. Modifier `resolveProductId()` (`server/services/variants.ts`) pour que :
1. Si `normStr(rawName)` est vide ou trop courte (ex: < 2 caractères utiles) après normalisation → NE PAS matcher, retourner `null`/`undefined` explicitement.
2. Si plusieurs produits du catalogue partagent EXACTEMENT le même `normStr()` (ambiguïté réelle, pas un bug de regex) → NE PAS choisir le premier au hasard ; soit utiliser un critère de départage plus fort (SKU exact si fourni par le webhook, prix, variante), soit retourner `null` et laisser la commande dans un état "produit à confirmer manuellement" plutôt que de deviner.
3. Toute commande dont le produit n'a pas pu être résolu avec confiance doit être visible quelque part dans l'app (ex: badge "Produit non reconnu" dans Suivi des Colis) pour qu'un humain la lie manuellement — plutôt que de silencieusement associer un mauvais produit qui fausse ensuite tout le stock et la rentabilité.
